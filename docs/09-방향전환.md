## 가져온 것 — 관찰형 보고 (하나만)

### 왜 이것 하나인가
- **가장 싸다.** 화면 하나(`16 보고서 작성`)만 바꾸면 됨
- **인터뷰가 직접 지지하는 유일한 것** (`08` Q3). 완화는 **문장을 쓸 때** 일어나므로, 문장을 안 쓰게 하면 됨

- **BM과 충돌하지 않는다.** 매칭·수수료 구조를 건드리지 않음

## 별점을 되살린 이유 (앞 결정 철회)

`05-user-flow.md` 결정 2는 **"별점·후기 없음, 수령 확인 버튼 하나"**였다. **철회한다.**

근거였던 논리: *"별점이 있으면 시터가 나쁜 소식을 적을 때 점수가 깎인다"*
→ **인터뷰가 이 전제를 깼다.** 시터는 불이익 때문이 아니라 **"안심시키는 게 좋은 서비스라 여겨서"** 완화했다 (`08` Q3).
**완화의 원인이 애초에 별점이 아니었으므로, 별점을 없애도 완화는 남는다.** 없애서 얻는 게 없다.

우리가 만든 장치는 둘이었고, 인터뷰 이후 유효한 건 하나뿐이다.

| 장치 | 겨냥 | 판정 |

| **관찰형 기록** | 판단을 물으면 완화된다 | **유효 → 채택** |

## 프로토타입 (`prototype/index.html`)

**구현 범위 — 차별점이 도는 한 바퀴만.** 24화면 전부가 아니다.

```
시터: 돌봄 → 보고서 작성(활동 칩 + 오늘의 관찰 3행)
  → 보호자: 보고서 열람(비-최상값 강조) → 후기(별점 + 칩 6개)
  → 공개: 프로필 검증의 「이상 보고 N번」에 반영
```

| 항목 | 상태 |
|---|---|
| 역할 전환 | `시터 / 보호자 / 공개` + 초기화 버튼 (프로토타입 전용) |
| 저장 | `localStorage` 키 `petcare.proto.v1`. 새로고침 후 유지 확인됨 |
| 집계 규칙 | **관찰값 중 하나라도 비-최상이면 「이상 보고」 1건.** 전부 최상이면 돌봄 횟수만 +1 |
| 시작값 | 142회 / 12번 (시안 목업과 동일) |
| 전송 조건 | 관찰 3가지를 모두 골라야 전송 가능 |

**검증 (브라우저에서 실제로 돌림)**
- 비-최상 2개(절반·조용함) 포함 → `142/12 → 143/13` ✅ 보호자 화면에 `절반`, `조용함`이 강조 표시됨
- **전부 최상값 → `143/13 → 144/13`** ✅ 돌봄 횟수만 오르고 이상 보고는 그대로

**구현하지 않은 것:** 시안의 나머지 20화면(온보딩·계정·검색·예약·상담채팅·비상대응 3화면 등), 사진 첨부, 인증, 결제.

# 2차 수정 — 지정 인증 사진 (2026-08-04)

## 무엇이 틀렸나

관찰값 3행은 **「관찰을 묻는다」고 해놓고 여전히 판단을 요구**했다.
`다 먹음 / 절반 / 거의 안 먹음` 중에서 고르려면 시터가 "이게 절반인가?"를 판정해야 하고,
애매하면 좋은 쪽으로 반올림한다. 실제 시터의 답: **"전부 첫 번째를 고를 우려가 있겠어"** (`08` 인터뷰 #2)

## 바꾼 것

**시터가 고를 값을 없앴다. 찍을 대상만 지정한다.**

| | 밥그릇 | 배변 패드 | 아이 |
|---|---|---|---|
| 필수 | ✅ | ✅ | 선택 |
| 왜 | 얼마나 먹었는지 | 배변 상태 | 지금 모습 |

- **대상을 지정**하는 것이 핵심이다. 자유 사진이면 좋아 보이는 순간만 골라 찍는다 (창고 사건 = 고양이 한 마리 사진만 옴)
- **판정은 보호자가 한다.** 귀가해서 그릇과 패드를 직접 보고 `사진 그대로였어요 / 사진과 달랐어요`

## 지표도 바꿨다

| | 전 | 후 |
|---|---|---|
| 1순위 지표 | 비-최상 관찰값 비율 ≥20% | **보호자 대조율 / 불일치율** |
| 공개 프로필 문구 | "이상을 12번 먼저 알렸습니다" | **"142회 돌봄 중 보호자가 128회 직접 대조했고, 그중 126회가 사진과 같았습니다"** |
| 후기 칩 | 「안 좋은 것도 알려줘요」 | **「있는 그대로 찍어줘요」** |

**왜 지표를 바꿨나:** 「비-최상 ≥20%」는 아이가 실제로 대체로 괜찮으면 영원히 미달이고, 제품이 실패한 것처럼 보인다.
완화는 직접 측정할 수 없다. **보호자가 대조해서 "달랐다"고 한 비율**이 왜곡의 유일한 측정 가능 지표다.

「불일치 0건」을 자랑하지 않고 **대조 횟수와 불일치를 함께** 표시한다 — 무사고 자랑의 함정을 피한다.

- **그릇을 치우고 찍거나, 안 먹은 날은 아예 안 보낸다** → 대상 지정으로도 못 막음. 시각 기록·미전송 표시가 필요
- **보호자가 대조를 안 한다** (`사진 그대로였어요`를 습관적으로 누름) → 판정이 형식이 됨. 대조율 지표가 의미를 잃음
- **사진 용량 때문에 실사용이 안 된다** → 서버 저장 필요. localStorage로는 한계

## 남은 미검증 가정 (갱신)

| 가정 | 상태 |
|---|---|
| 지정 사진이 값 선택보다 완화를 덜 유발한다 | **[가설]** 이번 수정의 전부가 여기 걸림. 검증 안 됨 |
| 보호자가 실제로 귀가 후 대조한다 | **[추측]** |
| 시터가 사진 2컷을 부담스러워하지 않는다 | **[추측]** — Q7 기준선에 걸려 있음 |
| 보호자 인터뷰 **0명** | 여전히 **가장 큰 구멍** |

# 3차 수정 — 일정 기반 인증 (2026-08-04)

## 무엇이 틀렸나

밥그릇·배변 패드를 **기획이 필수로 고정**했다. 그런데 그날 밥을 안 주는 돌봄이 있고, 자율급식 하는 집도 있다.
그러면 시터는 못 보내거나 아무거나 찍게 된다.

> **대상을 지정한 건 맞았다. 지정하는 주체가 틀렸다.**

## 바꾼 것 — 사용자 제안

**보호자가 일정을 정하고, 항목마다 찍을 대상이 자동으로 붙는다.**

| 항목 | 찍을 것 |
|---|---|
| 밥 | 밥그릇을 찍어주세요 |
| 산책 | 산책 중 한 장 |
| 배변 | 배변 패드를 찍어주세요 |
| 약 | 약 먹은 뒤 한 장 |
| 놀이 | 노는 모습 한 장 |

보호자가 `밥 10:00 / 산책 12:00 / 밥 17:00` 처럼 짜면, 시터 화면에 그 타임라인이 뜨고 각 항목에 「지금 인증」 버튼이 붙는다.

### 이 변경이 한 번에 푸는 것 3가지
1. **그 집에 없는 걸 요구하지 않는다**
2. **시점이 붙는다** → `05-user-flow.md` 구멍 2(퇴근 후 몰아 찍기)가 자동으로 막힌다. **시각은 시터가 고칠 수 없다**
3. **버렸던 「시점 순 인계 카드」가 되살아난다** → 근본 원인 **V2**에 대한 답이 원래 이것이었다

## 설계 결정 — 지연에 벌점을 주지 않는다

예정 10:00, 실제 10:12면 **`10:12` 를 그대로 기록하되 "지각"으로 표시하지 않는다.**
못 한 항목이 있어도 완료할 수 있다. 벌점을 주면 Q7의 "숙제처럼 느껴지지 않게"가 무너지고,
시간에 쫓겨 대충 찍게 된다. **[미검증 가정]**

## 지표

| | 내용 |
|---|---|
| **일정 인증률** | 보호자가 정한 N개 항목 중 몇 개를 그 자리에서 인증했나 — **완화 불가.** 시각과 개수는 못 고침 |
| **보호자 대조율 / 불일치** | 유지 |

공개 프로필: *"보호자가 정한 515개 항목 중 500개를 그 자리에서 사진으로 인증했습니다."*

## 검증 (브라우저에서 실제 파일 입력으로)
- 일정 추가·삭제·시각 변경 동작 ✅
- 항목 종류를 바꾸면 **찍을 대상 문구가 따라 바뀜** ✅
- 인증 시 **실제 시각이 자동 기록**되고 예정 시각과 나란히 표시됨 ✅
- 3건 중 2건만 인증하고 완료 → 보호자 화면에 「인증 없음」 1건 표시 ✅
- 공개 프로필 집계 `512/498 → 515/500`, 대조 `142/128/126 → 143/129/127` ✅
- 저장 4KB (사진 320px·JPEG 0.68) ✅

## 이 수정이 틀렸다면 무엇이 관찰되는가
- **보호자가 일정 짜는 걸 귀찮아한다** → 부 사용자에게 게이트를 건 것. 과거에 한 번 틀렸던 패턴과 같은 모양. 기본 템플릿만으로 넘어가게 해야 함
- **시각 때문에 시터가 쫓긴다** → 벌점을 안 줘도 압박이 생김. Q7 기준 재위반
- **시터가 미리 몰아서 찍어둔다** (아침에 다 찍고 나중에 올림) → 시각 기록은 업로드 시각이라 못 막음. 촬영 시각(EXIF) 필요
- **인증률이 항상 100%로 나온다** → 지표가 변별력을 잃음. 그러면 이것도 「무사고 자랑」과 같아짐

# 4차 수정 — 프로필 + 실시간 확인 (2026-08-04)

## A. 시터 프로필 — 두 칸으로 분리

버렸던 3층 프로필 중 **「가져온 후기」가 실제 요구로 되살아났다** (`08` 인터뷰 #4).
검증이 안 되므로 **확인된 것과 자리를 나눈다.**

| 칸 | 라벨 | 내용 | 시터가 수정 가능? |
|---|---|---|---|
| ① | **이 서비스에서 확인됨** (파란 배지) | 신원 인증 / 일정 인증률 / 실시간 확인율 / 보호자 대조율 | **불가.** 자동 계산 |
| ② | **시터 본인이 올림 · 이 서비스가 확인하지 않음** (회색 배지) | 당근 알바 등에서 가져온 후기 + **캡처(필수)** | 가능 |

- **캡처 필수** — 글만 옮기면 지어낸 것과 구분이 안 된다. 캡처가 있으면 보호자가 직접 보고 판단할 수 있고 위조 비용이 오른다
- **"검증됨"이라고 쓰지 않는다.** 서비스가 진위를 확인하지 않는다는 사실을 화면에 명시
- 출처: 당근 알바 / 펫플래닛 / 와요 / 도그메이트 / 지인 소개 / 기타
- **[미확인] 당근 알바 후기에 공개 링크가 있는지 모른다.** 있으면 캡처보다 강함

## B. 실시간 확인 — 구멍 8을 메운다

3차 수정의 기각 조건이었던 **"미리 몰아 찍어두고 나중에 올리면 못 막는다"**에 대한 답.

```
시터가 10:03 인증  →  보호자에게 즉시 뜸  →  보호자가 10:05 [확인했어요]
                                              또는 [물어볼게요]
```

- **확인 시각이 함께 남는다.** 보호자가 그 자리에서 목격했다는 기록이 생기면 사후 조작이 어려워진다
- 시터 타임라인에 `보호자 확인` / `보호자 질문` / `확인 대기`가 표시된다
- **[물어볼게요]** — 이상하면 귀가 전에 그 자리에서 물을 수 있다. 귀가 후엔 늦다
- **보호자가 못 봐도 시터에게 불이익 없음.** 자는 중일 수도 회의 중일 수도 있다

**완전한 해결은 아니다.** 촬영 시각(EXIF)은 여전히 안 본다. **조작 비용을 올릴 뿐이다.**

## 지표 추가

> "인증 500건 중 414건은 보호자가 받은 그 자리에서 확인했습니다."

## 검증 (브라우저에서 실제로)
- 인증 → 보호자 화면에 즉시 노출, `확인했어요 / 물어볼게요` 액션 ✅
- 확인 시 시각 기록 `21:56 확인했어요` ✅ / 질문 시 `21:56 물어봤어요` ✅
- **시터 타임라인에 역방향 반영** (`확인 대기` → `보호자 확인`) ✅
- 후기 담기: **내용만으로는 잠김, 캡처를 올려야 등록 가능** ✅
- 공개 프로필에 두 칸이 서로 다른 라벨로 분리 노출 ✅
- 공개 지표 `인증 500건 중 414건 실시간 확인` ✅

## 함께 고친 버그 (실사용을 막던 것)
**스키마가 바뀌면 예전 localStorage가 앱을 통째로 깨뜨렸다.** 얕은 병합이라 baseline의 새 필드가 사라져
`render()`가 던지고 화면이 백지가 됐다. → `load()`에서 baseline·impDraft를 항목별로 병합하도록 수정.

## 이 수정이 틀렸다면
- **보호자가 실시간 확인을 안 누른다** → 장치가 작동하지 않음. 알림 설계가 따로 필요
- **습관적으로 「확인했어요」만 누른다** → 목격 기록으로서의 가치는 남지만 판정으로서는 형식이 됨
- **시터가 「확인 대기」를 압박으로 느낀다** → Q7 기준 재위반
- **가져온 후기를 보호자가 「확인됨」과 구분하지 않는다** → 두 칸 분리가 무의미. 오히려 자기주장을 포장해주는 꼴

# 5차 수정 — 앱 촬영 강제 + 시각 워터마크, 후기 분리 (2026-08-04)

## A. 후기를 대조 판정에서 떼어냈다

**사용자 지적:** "사진 인증 확인 후에 후기 작성으로 넘어가는 건 빼도 될 것 같아. 후기는 돌봄이 끝나고 써도 될 것 같아."

판정 직후 후기 화면이 자동으로 뜨면 **그것도 "지금 해야 하는 일"이 된다.**
→ 판정하면 그 자리에 머문다. 후기는 `[후기 쓰기]` 로 선택 진입.

**보호자의 필수 입력은 이제 두 개뿐이다:** 일정 설정(1회) + 대조 판정(1회).
실시간 확인은 누를 것이 없고(열면 자동 기록), 후기는 선택이다.

## B. 앱 카메라 강제 + 촬영 시각 워터마크 ★ 구멍 8 정면 대응

**사용자 요구:** "사진은 무조건 앱을 통해서 촬영하도록 하고 싶어. 시간과 날짜 인증마크도 붙도록."

| | 구현 |
|---|---|
| 갤러리 차단 | 인증 사진 input에 `capture="environment"` → 모바일에서 **카메라가 바로 열린다** |
| 워터마크 | 촬영 직후 canvas로 **하단 띠에 `2026.08.11 12:11` + `앱 촬영`** 을 픽셀에 굽는다 |
| 저장 | `proofs[id].stamp` 에 촬영 시각 문자열도 별도 보관 |

**후기 캡처는 예외다.** 그건 당근 알바 앱 스크린샷이라 갤러리에서 와야 한다.
→ 인증 사진만 카메라 강제·워터마크, 후기 캡처는 그대로.

### 한계 — 과장하지 말 것
- **`capture`는 힌트다.** 데스크톱 브라우저는 무시하고, 일부 모바일 브라우저에서는 우회 가능
- **워터마크는 우리 앱이 그린 것이라 암호학적 증거가 아니다.** 화면을 다시 찍으면 뚫린다
- **여전히 EXIF 촬영 시각은 안 본다**

→ 조작을 **불가능하게** 만드는 게 아니라 **비용을 올리는** 장치다. 문서에 그렇게 적는다.

## 검증 (브라우저에서 실제로)
- 인증 input `accept=image/* capture=environment` ✅ / 후기 캡처 input `capture=null` ✅
- 워터마크가 **픽셀에 실제로 박힘** — 하단 42px 띠의 어두운 비율 0.89, 흰 글자 비율 0.076 ✅
- 저장된 stamp `2026.08.11 12:11` ✅
- 판정 후 후기로 자동 이동하지 않음. `[후기 쓰기]`는 선택 ✅

## 이 수정이 틀렸다면
- **시터가 앱 카메라를 불편해한다** (평소 쓰던 카메라 앱이 아님) → Q7 기준 재위반
- **어두운 곳·급한 상황에서 앱 카메라가 느려 인증을 포기한다** → 인증률 하락
- **워터마크가 사진을 가려서 보호자가 확인을 못 한다** → 띠 높이·투명도 조정 필요
- **화면 재촬영으로 뚫는 사례가 나온다** → 서버측 EXIF 검증 필요

# 6차 수정 — 판정을 항목별로 (2026-08-04)

## 무엇이 틀렸나

대조 판정이 **돌봄 전체에 1회**였다. 사진 3장을 보고 `사진 그대로였어요` 하나로 뭉뚱그렸다.

> **밥은 맞았는데 배변이 달랐으면 표현할 방법이 없었다.**

## 바꾼 것 — 사용자 요구

**인증 사진 한 장마다 따로 판정하고, 그 판정이 보고서에 누적된다.**

```
10:00 밥   [사진]  → 12:17 사진 그대로였어요     ← 항목별로 따로
12:00 산책 [사진]  → 12:17 사진과 달라요
17:00 밥   인증 없음
                     요약: 예정 3건 중 2건 인증 · 판정 2건 (일치 1)
```

- 「지금 오는 인증」 화면에서 사진마다 `[사진 그대로였어요] [달라요]`
- **그때그때 해도 되고 나중에 해도 된다.** 안 해도 시터에게 불이익 없음
- 「오늘의 기록」은 **판정 누적 결과를 보는 요약**이 된다 (전체 판정 버튼 없음)
- 미판정이 남아 있으면 상단에 `판정하러` 버튼으로 되돌아갈 수 있다

### 「물어볼게요」를 없앴다
`달라요`와 역할이 겹쳤다. **판정 두 개로 통합**했다 — 다르면 그게 곧 이의 제기다.

### 시터가 보는 것
`열람 전 → 보호자 열람 → 보호자 일치 / 보호자 이의` (항목별)

## 지표도 항목 단위로

| | 전 | 후 |
|---|---|---|
| 공개 문구 | "142회 **돌봄 중** 128회 대조, 126회 일치" | **"인증 500건 중 464건을 보호자가 사진 한 장씩 대조했고, 그중 459건이 같았습니다"** |

돌봄 단위보다 **분모가 커지고 해상도가 올라간다.** 어느 항목에서 어긋났는지도 남는다.

## 검증 (브라우저에서 실제로)
- 항목마다 `[사진 그대로였어요] [달라요]` 노출 ✅
- **밥=일치 / 산책=이의로 섞어서 판정 가능** ✅ (이전 구조에선 불가능했던 것)
- 시터 타임라인에 `보호자 일치` / `보호자 이의` 항목별 반영 ✅
- 보고서에 누적 표시 + 요약 `판정 2건 (일치 1)` ✅
- 공개 집계 `462/458 → 464/459` ✅ (2건 판정, 1건 일치)

## 이 수정이 틀렸다면
- **판정 버튼이 늘어 보호자가 부담을 느낀다** → 다시 1회로 묶거나, 판정을 아예 선택으로 낮춰야 함
- **미판정이 대부분으로 남는다** → 대조율 지표가 의미를 잃음
- **`달라요`를 눌러도 그다음에 할 게 없다** → 이의 이후 흐름(시터 소명·환불 등)이 없음. **미설계**

# 7차 수정 — 이의 → 소명 → 해소 흐름 (2026-08-04)

## 왜 필요했나

6차에서 `달라요` 버튼을 만들어놓고 **그 뒤에 아무것도 없었다.** 이의를 제기해도 갈 곳이 없었다.
그리고 사용자 지적: **"보호자가 잘못 눌렀을 경우도 생길 수 있을 것 같아."**

**잘못 눌렀을 때 되돌리기 어려우면, 보호자는 아예 `달라요`를 안 누르게 된다.**
그러면 대조 판정 전체가 무의미해진다. 되돌리기가 이 기능의 성패를 가른다.

## 흐름

```
보호자 [달라요]
   ↓
무엇이 달랐나요?  ← 사유 6개 프리셋 (밥이 그대로 / 패드가 깨끗 / 다른 곳 같아요 / 시간이 안 맞아요 / 상태가 달랐어요 / 그 밖의 이유)
   ↓                 이 단계까지 [잘못 눌렀어요]로 흔적 없이 되돌릴 수 있다
시터에게 전달 → 시터가 소명 (한 줄)
   ↓                 소명이 오면 되돌리기는 사라진다 — 상대가 이미 답했으므로
보호자 [이해했어요] / [그래도 다릅니다]
   ↓
해소됨 / 해소되지 않음  → 양쪽 기록 모두 보존
```

## 잘못 눌렀을 때 — 설계 규칙

> **시터가 소명하기 전까지는 흔적 없이 되돌릴 수 있다. 소명이 온 뒤에는 되돌릴 수 없다.**

- 오조작은 흔하다. 매번 「정정함」이 남으면 보호자가 판정 자체를 꺼리게 된다
- 하지만 상대가 이미 시간을 들여 답했는데 조용히 지우는 건 불공정하다
- **기준을 "상대가 반응했는가"로 잡았다.** 시간이 아니라 상호작용을 기준으로 삼는다

## 해소되면 일치로 정정된다
`이해했어요`를 누르면 그 항목의 판정이 **일치로 바뀐다.** 오해였다면 시터가 손해 볼 이유가 없다.
단 **이의가 있었다는 사실과 소명 내용은 지워지지 않는다.**

## 공개 프로필

> **"이의 6건 중 5건은 시터 소명으로 해소됐습니다. 남은 1건도 기록에 그대로 남아 있습니다."**

- **소명이 작동했다는 것 자체가 신뢰 신호다.** 이의 0건을 자랑하지 않는다
- 미해소도 숨기지 않는다 — 「사고 0건」 함정을 피하는 것과 같은 원칙

## 검증 (브라우저에서 전 구간)
- 판정 → **[잘못 눌렀어요] → 흔적 없이 복원** (판정 0건, 버튼 재노출) ✅
- `달라요` → 사유 6개 → 선택 → `시터 소명을 기다리는 중` ✅ (이 단계까지 되돌리기 가능)
- 시터 화면에 이의·사유 표시 → 소명 입력 → `보호자 확인을 기다리는 중` ✅
- 보호자가 소명 보고 `이해했어요` → **해소됨, 판정이 일치로 정정** ✅
- 시터 타임라인 `보호자 이의 → 해소됨` ✅
- 보고서 누적 `이의: 밥이 그대로 남아 있었어요 → 해소됨` ✅
- 공개 집계 `이의 5/해소 4 → 6/5` ✅

## 이 수정이 틀렸다면
- **되돌리기를 악용해 이의를 반복 제기·취소한다** → 시터가 소모됨. 취소 횟수 제한 필요
- **시터가 소명을 안 한다** → 이의가 영원히 「소명 대기」로 남음. 기한과 자동 처리 규칙 필요
- **`그래도 다릅니다` 이후에 아무것도 없다** → 환불·중재·신고 경로 **미설계.** 다음 과제
- **이의가 무서워 보호자가 애초에 안 누른다** → 대조율이 0으로 수렴. 지표로 감시

# 8차 수정 — 소명 기한 · 사진 없는 항목 · 확인/가짜 비대칭 (2026-08-04)

## A. 소명 기한 규칙

7차의 미해결: **시터가 소명을 안 하면 이의가 영원히 「소명 대기」로 남았다.**

```
이의 접수 → 24시간 뒤 한 번 더 알림 → 72시간 무응답 → 「소명 없음」으로 종결
```

- **자동으로 해소 처리하지 않는다.** (자동 확인 없음 원칙과 같은 계열)
- **자동으로 미해소 처리하지도 않는다.** 「해소되지 않음」과 「소명 없음」은 다른 사실이다
- 기한이 지나면 시터의 소명 입력이 닫히고, 보호자의 되돌리기도 사라진다
- 프로토타입에는 타이머가 없어 **「(프로토타입) 72시간 경과시키기」 버튼**으로 대체

**공개 문구:** *"6건 신고되어 4건은 소명으로 해소됐습니다. 소명하지 않은 것은 1건입니다."*
→ 해소·미해소·무응답을 **각각** 보여준다. 뭉뚱그리지 않는다.

## B. 사진은 없는데 실제로는 했을 때 ★

**사용자 지적:** "사진은 없는데 먹었을 수도 있을 것 같아."

기존엔 미인증이 **「인증 없음」** 하나로만 남아서, 실제로 했는데 못 찍은 경우가 억울해진다.

→ 시터가 **「사진 없이 설명 남기기」** 를 쓸 수 있게 했다.

**단, 인증으로 세지 않는다.**
- 화면에 `설명은 인증으로 세지 않습니다` 를 명시
- 인증률 분자·분모에 영향 없음
- 보호자 화면에는 `사진이 없어 대조할 수 없습니다` 로 표시 — 확인 버튼이 뜨지 않는다
- 공개 프로필에 **별도 줄**: *"사진 없이 남긴 설명 24건. 사진 인증과 따로 셉니다."*

**이게 핵심이다.** 설명을 인증률에 넣으면 **사진 안 찍고 설명만 쓰는 게 이득**이 된다.
자기신고와 검증된 것을 섞지 않는다는 원칙이 여기서도 적용된다.

## C. 확인 / 가짜 인증 — 비대칭 설계

**사용자 요구:** "확인 마크 / 가짜 인증으로 바꿔줘. 웬만하면 확인마크를 클릭하도록 하고,
가짜 인증은 중요도를 작게. 진짜 가짜로 의심될 경우 누를 수 있을 정도로."

| | 전 | 후 |
|---|---|---|
| 일치 | `[사진 그대로였어요]` (동등) | **`[✓ 확인]`** — 42px 파란 채움 버튼 |
| 불일치 | `[달라요]` (동등) | **`가짜 인증 같아요`** — 30px 밑줄 텍스트, 배경 없음 |

두 선택지를 **같은 무게로 두면 안 된다.** 확인은 일상 동작이고, 가짜 신고는 시터가 소명해야 하는 무거운 사건이다.
화면에도 명시: *"「가짜 인증 같아요」는 정말 의심될 때만 눌러주세요 — 시터가 소명해야 하는 무거운 신고입니다."*

### 사유 프리셋도 교체
「무엇이 달랐나요?」(대조) → **「왜 가짜라고 보시나요?」**(진위)
`우리 집이 아닌 것 같아요 / 예전에 찍은 사진 같아요 / 그 시간에 오지 않은 것 같아요 / 밥이 그대로 남아 있었어요 / 배변 패드가 깨끗했어요 / 그 밖의 이유`

## 함께 고친 버그
`done` 목록에 사진 없는 항목이 들어오면서 헤더 집계가 `undefined.verdict`로 던졌고,
**`render()`가 죽어 화면이 이전 상태에 멈췄다.** 사용자에겐 "버튼이 안 먹는" 것처럼 보였을 버그.

## 검증 (브라우저에서 실제로)
- 확인 버튼 `높이 42px · 배경 #0066FF · 14px` / 가짜 버튼 `높이 30px · 배경 투명 · 12px` ✅
- 시터 설명 저장 → 인증 카운트는 `1/3` 그대로 (설명 미포함) ✅
- 보호자 화면에 `사진이 없어 대조할 수 없습니다` ✅
- 72시간 경과 → `소명 없음`, 시터 소명칸 닫힘, 되돌리기 사라짐 ✅
- 보고서 `가짜 신고: 예전에 찍은 사진 같아요 → 소명 대기` ✅

## 이 수정이 틀렸다면
- **「가짜 인증 같아요」가 너무 작아 아무도 못 찾는다** → 신고가 0으로 수렴, 장치가 죽음
- **반대로 남용된다** → 시터가 소모됨. 신고 횟수 제한 필요
- **설명만 쓰고 사진을 안 찍는 시터가 는다** → 인증률로 드러나지만, 보호자가 그 차이를 이해 못 하면 소용없음
- **72시간이 너무 짧다/길다** → 근거 없는 숫자다. **[추측]**

# 9차 수정 — 기록 화면 분리 · 숫자 3종 프로필 · 산책 왕복 인증 (2026-08-04)

## A. 시터 기록을 항목별 화면으로

**사용자 지적:** "오늘의 기록 페이지에서 3가지를 한꺼번에 업데이트해야 하는 구조"

한 화면에서 여러 항목을 동시에 만지는 구조였다. → **한 건씩 들어가서 기록하고 나오는 형태**로 바꿨다.

```
시터  일정 리스트 → [기록하기] → 그 항목만 있는 기록 화면 → 제출 → 리스트 복귀
보호자 제출 즉시 「지금 오는 인증」에서 그 자리에서 확인   ← 「판정하러」 이동 없음
      「모아보기」(오늘의 기록)에서 전체 진행 상황
```

- 리스트 행 상태: `사진 제출` / `설명만 제출` / `아직 기록 없음`
- 기록 화면에서 사진과 메모를 함께 넣을 수 있고, 사진 없이 메모만 제출하면 「설명만」이 된다
- 「오늘의 기록」은 **판정하는 곳이 아니라 모아보는 곳**이 됐다

## B. 공개 프로필을 숫자 3종 중심으로

경쟁사 검증(`10-경쟁사-검증.md`) 결과 **「사진 인증」은 차별점이 아니었다.** 이미 다 한다.
그래서 프로필의 주인공을 바꿨다.

| 순서 | 지표 | 예시 |
|---|---|---|
| 1 | **약속 이행** | `498 / 512` **97%** |
| 2 | **보호자 확인** | `462 / 498` **93%** — *"보낸 것과 확인된 것은 다릅니다"* |
| 3 | **신고와 해소** | `5건 중 4건 해소` (붉은색) · 소명 안 한 1건도 표시 |

그 아래 한 줄: *"실시간 영상은 그 순간만 보여주고 사라지지만 이 숫자는 남습니다."*

신원 인증·앱 촬영·열람·설명 건수는 **보조 지표로 강등**. 별점도 이름 옆 한 줄로 내림.

## C. 산책 왕복 인증 — 흔적이 안 남는 항목을 보강

**사용자 지적:** GPS는 **시터 폰의 위치**일 뿐 개가 함께 있다는 증거가 아니다.
그리고 산책은 밥·배변과 달리 **귀가 후 대조할 물리적 흔적이 없다.**

→ **나갈 때 / 들어올 때 두 컷.** 두 워터마크의 시각 차이가 곧 **「밖에 있던 시간」**이 된다.

```
밖에 있던 시간 24분 — 두 사진의 시각 차이입니다
```

- 시각은 앱이 박으므로 시터가 고칠 수 없다 → **GPS 없이도 지속시간이 증명된다**
- 한 장만 찍어도 제출은 되지만 「두 장을 다 찍어야 밖에 있던 시간이 남습니다」가 뜬다
- **「아이가 보이게」를 지시에 추가** — 전에는 `산책 중 한 장`이라 풍경만 찍어도 통과했다 (산책·약·놀이)

### GPS 대비
| | GPS | 두 컷 + 시각 |
|---|---|---|
| 증명하는 것 | 시터 폰의 위치 | **개와 함께 밖에 있던 시간** |
| 개가 함께였나 | **증명 못 함** | 사진에 찍혀야 함 |
| 속이는 법 | 혼자 걷기 | 그 시각에 그 개를 두 번 찍어야 함 |

## 검증 (브라우저에서 실제로)
- 리스트 → 기록 화면 → 사진 제출 / 설명만 제출 → 리스트 복귀 ✅
- 보호자가 **이동 없이 그 자리에서** 확인 ✅
- 산책 슬롯 2개(`나갈 때` / `들어올 때`), 지시 문구 반영 ✅
- 시각 차 계산: 24분→24, 7분20초→7, 둘째 컷 없음→표시 안 함, 역순→0 방어 ✅
- 공개 프로필 히어로 3개 + 진행 바, 보조 지표 5줄 ✅

## 함께 고친 버그
- 기록 화면에서 **메모만 입력하면 제출 버튼이 안 풀렸다** (`oninput`에서 재렌더를 안 함).
  포커스 유지를 위해 전체 재렌더 대신 버튼 상태만 갱신하도록 수정
- 「모아보기」로 가는 버튼 라벨이 `기록 확인`이었던 것을 `모아보기`로 정정

## 이 수정이 틀렸다면
- **항목마다 화면을 오가는 게 더 번거롭다** → 한 화면 인라인이 나았던 것. Q7 기준 재검토
- **산책 두 컷이 부담이다** → 산책만 요구가 2배다. 한 컷으로 되돌려야 함
- **집 안에서 두 장 찍고 24분 뒤 또 찍으면 못 막는다** → 배경으로만 구분된다. **미해결**
- **보호자가 숫자 3종을 안 보고 별점만 본다** → 프로필 재배치가 무의미

# 10차 수정 — 텍스트 인증도 확인 대상 · 포인트 가중치 (2026-08-04)

## 무엇이 문제였나

8차에서 「사진 없이 설명」을 만들었지만 **보호자가 확인할 수 없었다** (`사진이 없어 대조할 수 없습니다`).
그래서 사진을 못 찍은 항목은 **아무리 설명을 잘 써도 영원히 미확인**으로 남았다.
설명이 인증률에서도 빠져 있었으니, 시터 입장에선 **쓸 이유가 없는 기능**이었다.

## 바꾼 것 — 사용자 제안

> **사진 인증 = 1점, 텍스트 인증 = 0.5점.** 텍스트도 확인 대상이 된다.

| | 사진 | 설명만 |
|---|---|---|
| 점수 | **1점** | **0.5점** |
| 보호자 확인 | 가능 | **가능** (전에는 불가) |
| 신고 버튼 문구 | `가짜 인증 같아요` | `사실과 달라요` |

**두 마리를 동시에 잡는다:**
- 설명이 **인정받는다** → 못 찍은 상황이 억울하지 않다
- 설명이 **절반만 인정된다** → 사진을 안 찍는 게 이득이 되지 않는다

## 지표 재정의

| | 전 | 후 |
|---|---|---|
| 약속 이행 | `498 / 512` (건수) | **`488 / 515점`** (포인트) |
| 보호자 확인 | 사진 제출분만 | **전체 제출분** (사진 + 설명) |
| 보조 지표 | "사진 없이 남긴 설명 23건 (인증과 별도)" | **`사진 인증 · 1점 476건` / `설명 인증 · 0.5점 24건`** |

공개 프로필 문구: *"사진은 1점, 사진 없는 설명은 0.5점으로 셉니다."*
*"설명도 확인 대상이지만 사진의 절반만 셉니다. 사진을 안 찍고 설명만 쓰는 것이 이득이 되지 않게 하기 위해서입니다."*

## 저장 구조 통합 (리팩터링)

사진(`proofs`)과 설명(`notes`)이 **다른 곳에 저장돼 있어서** 설명에 확인·신고를 붙일 수 없었다.
→ **모든 제출을 `proofs` 하나로 합쳤다.** `photo`가 `null`이면 설명만 제출이다.
`load()`에 예전 구조(`notes`)를 옮기는 마이그레이션을 넣어, 기존 저장 상태도 그대로 열린다.

# 11차 수정 — 소명 발견성 · % 중심 프로필 · 재제출 시 확인 무효화 (2026-08-04)

## A. 소명 경로가 있는데 못 찾았다

**사용자 지적:** "소명 대기 할 수 있는 방법이 없는 거 같음."

확인해보니 **경로는 살아 있었다.** 문제는 **발견성**이었다 —
소명 입력칸이 「오늘의 돌봄」 리스트 안에 파묻혀 있고, **알림이 없어 신고가 온 줄도 몰랐다.**

→ 두 겹으로 고쳤다.
1. **상단 경고 배너** — `소명이 필요한 신고 N건` + `[소명하러 가기]`. 화면 켜면 바로 보인다
2. **소명 전용 화면** — 「기록하기」와 같은 패턴. 신고 사유 + **내가 보낸 인증(사진·촬영시각)** 을 함께 보여줘 무엇을 보고 답하는지 알 수 있게 함
3. 기한 지난 건은 화면이 닫히고 `72시간이 지나 소명 기회가 닫혔습니다`로 바뀐다

**교훈:** 기능이 있는 것과 **찾을 수 있는 것**은 다르다. 리스트 안에 인라인으로 넣으면 없는 것과 같다.

## B. 공개 프로필 — % 먼저, 횟수는 괄호

```
약속 이행     95%  (487.5 / 515점)
보호자 확인   93%  (463 / 499건)
```

**「신고와 해소」는 히어로에서 뺐다** (사용자 요청). 다만 **완전히 숨기지 않고 보조 지표로 내렸다** —
`가짜 인증 신고 = 6건 중 5건 해소 · 무응답 1`

> **왜 완전히 안 지웠나:** 경쟁사 검증에서 우리 차별점 중 하나가
> *"분쟁이 제품 안에 있고 공개된다 — 경쟁사는 「사고 0건」을 자랑하지 「신고 6건 중 4건 해소」를 자랑하지 않는다"* 였다.
> 완전히 숨기면 그 차별점이 사라진다. **눈에 덜 띄게 하되 볼 수 있게** 두는 절충.
> 아예 빼는 것도 선택지로 남겨둔다.

## C. 재제출하면 확인이 무효화된다 ★ 구멍 수정

엣지 케이스 검증 중 발견:

> **보호자가 확인한 뒤 시터가 그 항목을 다시 기록하면, 「확인됨」이 유지된 채 사진만 바뀌었다.**

핵심 규칙 4(**보호자가 확인한 것 ≠ 시터가 보낸 것**)가 깨진다.
확인을 잘 받아놓고 사진만 갈아끼우면 그만이었다.

**수정 — 두 규칙을 동시에 지킨다:**

| | 재제출 시 |
|---|---|
| `verdict` (확인) | **무효화.** 다시 확인받아야 한다 |
| `seen` (열람) | 초기화. 새 사진은 다시 봐야 한다 |
| `dispute` (신고) | **유지.** 재기록으로 신고를 지울 수 없다 |

그리고 **숨기지 않는다:**
- 기록 화면에 사전 경고 — `다시 제출하면 보호자 확인이 취소되고 다시 확인받아야 합니다`
- 보호자 화면에 `N회 다시 제출` 배지 + `이전 제출(14:10)을 지우고 다시 올렸습니다`
- 공개 프로필 보조 지표에 **`다시 제출 N건`** 집계

재제출 자체는 잘못이 아니다(흐릿하게 찍혀 다시 찍을 수 있다). **다만 유독 많으면 보호자가 판단할 수 있어야 한다.**

## 치명 2건

### #1 「한 바퀴 다시 돌기」 후 프로필 진입 시 `render()`가 던진다

```js
S = Object.assign(structuredClone(SEED), { baseline: counts() });   // ← counts()에는 rating이 없다
...
const rating = () => { const b = S.baseline; return { avg: b.rating.toFixed(1) ... }  // TypeError
```

`counts()`의 반환 키에는 `rating`·`reviews`가 **없다**(대신 쓰지 않는 `earned`·`submitted`가 있다).
그걸 baseline에 **통째로 대입**해서 다음 바퀴부터 `b.rating`이 `undefined`가 된다.
`render()`가 던지면 **DOM을 하나도 갱신하지 못하고 이전 화면이 남는다** → 앱이 멈춘 것처럼 보인다.

> **뼈아픈 점:** `load()`에는 *"baseline은 얕은 병합으로 덮이면 새 필드가 사라진다"* 는 주석까지 달아 고쳐놨는데,
> **정작 baseline을 만드는 쪽은 안 고쳤다.** 같은 실수를 반대편에서 반복했다.

**수정:** 항목별 승계 + `imported`·`sitter` 보존(라운드와 무관한 자산이 지워지던 것도 함께).

### #2 재제출 후 「확인」이 신고·소명 이력을 삭제한다

`record()`는 재제출 시 `dispute`를 **일부러 살려두는데**, `ownerVerdictBlock`이

**보호자에게 이력이 보이지도 않으므로 오조작이 아니라 정상 조작으로 발생한다.**
제품의 유일한 차별점("분쟁을 공개한다")이 **2클릭에 사라진다.**

**수정:** 끝난 신고는 **「지난 신고 기록」으로 언제나 먼저, 읽기 전용 표시**. 확인해도 `dispute`는 유지.

| 13 | `recDraft`/`replyDraft`가 정리 안 되고 누적 (제출 안 하고 나가면 base64 사진이 잔류) | #12과 함께 다뤄야 함 |
| 16 | `shrink()`에 실패 경로 없음 — 디코드 실패 시 **버튼을 눌러도 아무 일도 안 일어남** | 실제 서비스 전환 시 필수 |

## 교훈
1. **같은 함정을 반대편에서 반복했다** (#1). 한쪽을 고쳤다고 다른 쪽이 안전한 게 아니다

# 13차 수정 — 시간 알림 · 즉시 전달 · 추가 활동 (2026-08-11)

## A. 시간이 되면 알림 + 해당 인증 화면 (사용자 요구)

> "10시에 밥을 줘야 될 경우 밥시간이에요! 하면서 해당 인증 화면만 뜨는 거지"

- **시터:** 예정 시각이 되면 `🔔 밥시간이에요!` 배너 → `[지금 인증하기]` → **그 항목의 기록 화면으로 바로 이동**
- **보호자:** 시터가 제출하는 즉시 `🔔 방금 인증이 도착했어요` 배너 + 건수

**프로토타입 한계:** 실제 푸시는 서버가 필요하다. 여기서는
`(프로토타입) 밥시간 알림 울리기` 버튼으로 시뮬레이션하고, 도착 배너는 미열람 제출 수로 계산한다.
**실서비스에서는 푸시 알림을 탭하면 해당 화면이 딥링크로 열리는 구조가 된다.**

## B. 추가 활동 (사용자 요구)

> "보호자가 설정한 인증 이외의 활동들을 펫시터가 추가로 기입할 수 있도록"

- 시터 홈에 「추가로 한 일」 카드 + `[추가 활동 남기기]` → 사진(선택, 앱 카메라·워터마크) + 내용
- 보호자 실시간 화면과 공개 프로필에 노출

**설계 결정 — 약속 이행 점수에 넣지 않는다:**
> 추가 활동을 점수에 넣으면 **어려운 일정 대신 쉬운 추가 활동으로 점수를 부풀릴 수 있다.**
> 「보호자가 정한 것」과 「시터가 자발적으로 한 것」은 다른 종류의 신호다 — 섞지 않고 따로 센다.
> 공개 프로필: `추가 활동 32건 (점수와 별개)`

## 함께 고친 것
- **`bubble` 아이콘 누락** — 아이콘 16종으로 줄일 때 빠뜨려 「소명 보내기」 버튼 아이콘이 안 보였다. 추가 + 캐시 버스터(`?v=2`)
- **도착 배너 순서 버그** — 자동 열람 처리가 배너 계산보다 먼저 돌아 **배너가 영원히 안 뜨는 상태**로 처음 구현했다. fresh 계산을 열람 처리 앞으로 이동

## 검증 (브라우저)
- 알림 배너 → `[지금 인증하기]` → **해당 항목 기록 화면 직행** ✅
- 추가 활동 작성 → 시터 홈 · 보호자 화면 · 공개 프로필 노출 ✅
- 도착 배너: 첫 방문에 뜨고 재방문 시 사라짐 ✅
- 공개 집계 `추가 활동 32건 (점수와 별개)` ✅

## 이 수정이 틀렸다면
- **알림이 너무 잦아 시터가 끈다** → 시간 압박은 Q7 위반. 알림 빈도·묶음 설계 필요
- **추가 활동이 자기 홍보 피드가 된다** → 「내 강아지와의 일상」에서 걱정했던 것과 같은 문제. 개수 제한 검토
- **보호자가 추가 활동을 점수로 오해한다** → "점수와 별개" 문구가 안 읽히면 구분 표시 강화

# 14차 수정 — 「먼저 챙긴 순간」 + 고마워요 (2026-08-11)

## 무엇이 틀렸나 (인터뷰 #5)

13차의 "추가 활동 · 점수와 별개"에 대한 실제 시터의 답:

|---|---|---|
| 이름 | 추가 활동 | **먼저 챙긴 순간** |

사실 보고는 「일정 인증」으로. **같은 동기가 두 채널로 분리되어 각자 옳은 곳으로 흐른다.**

- 고마워요 받은 순간의 지우기 버튼 사라짐 ✅
- 공개 `먼저 챙긴 순간 32건 · 보호자 고마워요 28` ✅

- **"고마워요 수"가 사실상 별점이 된다** → 시터 간 비교 지표로 굳으면 완화 압력이 되살아남

# 15차 수정 — 리액션이 곧 확인 (2026-08-11)

## 사용자 제안
> "인증 화면에서도 귀여워요·고마워요·안심돼요 등 리액션을 전송하면 어떨까?
> 인증 전송 – 확인, 이건 너무 딱딱한 거 같아"

## 설계 — 리액션과 확인을 합쳤다

**「귀여워요」를 눌렀다는 것은 사진을 봤고 받아들였다는 뜻이다.**
→ 리액션 = `verdict { matched: true, reaction }`. **회계(확인 집계)는 그대로 돌고 딱딱함만 빠진다.**

| 버튼 | 기록 |
|---|---|
| 😍 귀여워요 / 😌 안심돼요 / 💙 고마워요 | 확인 + 리액션 |
| ✓ 확인만 | 확인 (리액션 없음) — 감정 표현을 강요하지 않는 탈출구 |
| `가짜 인증 같아요` | 변함없이 작게, 신고 |

- 시터 화면: 「보호자 확인」 대신 **「😍 귀여워요」** — 어느 사진에 어떤 반응이었는지가 그대로 보임
- 모아보기·타임라인 배지에도 리액션 표시
- 공개 프로필: `받은 리액션 389개 (😍 😌 💙)` 보조 지표 추가
- 안내 문구: "마음 가는 대로 눌러주세요 — 어느 것을 눌러도 확인으로 기록됩니다"

**「확인만」을 남긴 이유:** 모든 사진에 감정을 강요하면 그것도 숙제가 된다.
그리고 리액션별 집계를 별점화하지 않기 위해 공개 표시는 총개수만 한다.

## 검증 (브라우저)
- 리액션 4종 + 가짜 신고 렌더 ✅
- 귀여워요 → `verdict {matched:true, reaction:'귀여워요'}` / 확인만 → reaction 없음 ✅
- 시터 타임라인 배지 `😍 귀여워요` / `확인됨` 구분 ✅
- 보호자 확인 집계에 리액션 확인 포함 (93% 유지) ✅
- 공개 `받은 리액션 389개` ✅

## 이 수정이 틀렸다면
- **리액션 개수가 시터 간 비교 지표(사실상 별점)가 된다** → 완화 압력 부활. 총개수만 표시를 유지할 것
- **보호자가 리액션 고르는 것도 귀찮아한다** → 「확인만」이 기본이 되고 리액션은 장식이 됨
- **「가짜 인증 같아요」가 리액션 줄에 묻혀 더 안 보인다** → 신고 접근성 재확인 필요

# 17차 수정 — 「돌봄 마치기」에 의미를 채움 (2026-08-11)

## 배경

사용자 질문 "돌봄 마치기 버튼의 의미가 뭐야?"에 답하다 드러난 사실:
**버튼의 의미가 절반쯤 비어 있었다.** 집계 확정만 하고, 종료 후 제출 구분(2차 수정에 있다가
일정 기반 개편 때 사라짐)도, 후기로 이어지는 흐름도 없었다.

**사용자 정의:** "모든 돌봄을 마친다. 약속된 일정과 제출 리스트가 끝나면
돌봄 마치기 클릭 후 종료 → 후기 작성 플로우로."

## 흐름

```
시터  0/3 → [아직 기록이 없습니다]  (비활성)
      1/3 → [돌봄 마치기 · 미기록 2건]  (누를 수는 있음 — 강요하지 않기 원칙 유지)
      3/3 → [돌봄 마치기]
       ↓ 클릭
      토스트 「오늘 돌봄을 마쳤어요」 + 시터 화면에 종료 배너
       ↓
보호자 모아보기: 🔔 오늘 돌봄이 끝났어요 → [후기 쓰기] (primary) / [나중에]
       ↓
      후기 등록 → 「후기가 등록되었어요」 → 공개 프로필
```

- **미기록이 있어도 마칠 수 있다** — 다만 버튼에 `미기록 N건`이 표시된다 (숨기지 않기)
- **종료 후 제출은 「종료 후 기록」 배지** — 실시간·모아보기 양쪽. 2차 수정의 사후 기록 개념 복원
- 후기를 이미 쓴 경우 모아보기 CTA는 [프로필 보러 가기]로 바뀜

## 검증 (브라우저 전 구간)
- 0/3 비활성 → 1/3 `미기록 2건` → 3/3 `돌봄 마치기` ✅
- 마치기 → 보호자 모아보기 직행 + 종료 배너 + 후기 primary ✅
- 후기 등록 → 토스트 → 공개 프로필 ✅
- 종료 후 재제출 → `late: true` 저장 + 배지 표시 ✅

## 작업 중 사고 2건 (기록)
1. **패치 스크립트의 assert 실패로 전체 변경이 통째로 저장 안 됨** — 검증에서 "적용됐는데 왜 안 되지"로 잡음.
   교훈: 여러 replace를 한 스크립트에 넣을 때 하나의 assert 실패가 전부를 날린다. 적용 목록을 반환하게 바꿈
2. **file:// 캐시가 index.html 자체를 물고 있어** 패치가 반영 안 된 것처럼 보임 — `?v=3` 쿼리로 우회.
   w-icon.js 때와 같은 증상. **프로토타입 검증은 항상 캐시 버스터를 의심할 것**

## 이 수정이 틀렸다면
- 미기록인데 마치는 시터가 많다 → `미기록 N건` 표시가 압박이 아니라 면죄부가 됨
- 보호자가 [나중에]만 누른다 → 후기 병목은 여전. 리마인드 필요

# 18차 수정 — 일정 화면 통합 · 사진 벌점 제거 · 느슨한 시간대 (2026-08-11)

## A. 일정 편집과 인증 안내 통합 (사용자 요청 2건)
- 「언제 무엇을 해주면 되나요?」와 「이렇게 인증됩니다」 두 카드가 **같은 항목을 중복 표시** → 한 카드로 합침
- 이어서 편집 행 아래 붙인 `📷 밥그릇을 찍어주세요` 안내도 **제거** (사용자: "필요 없을 것 같은데")
  — 촬영 안내는 **찍는 사람(시터)의 기록 화면**에서 보이면 된다. 보호자에겐 소음

## B. 사진 벌점 제거 — 0.5점 폐지 (사용자 제안)

> "사진 촬영은 필수가 아니어도 될 것 같아. 점수를 잘 받으려면 시터들이 자연스레
> 사진을 많이 찍을 테니까. 경쟁심리로 별점을 잘 받기 위해."

**10차의 0.5점 가중치를 철회한다.** 제출은 사진이든 설명이든 1건.

| | 10차 (벌점) | 18차 (경쟁) |
|---|---|---|
| 설명 제출 | 0.5점 — 감점으로 사진 유도 | 1건 — **감점 없음** |
| 사진 유인 | 점수 차이 | **시장 압력** — 리액션·후기·재의뢰가 사진에 몰림 |
| 안전장치 | 가중치 | **사진/설명 비율 공개** (`사진 인증 476건 / 설명 인증 25건`) |

우리의 반복된 교훈("형식으로 강제하지 말 것")과 일치한다. 벌점은 강제의 변형이었다.
**단, 비율 공개는 남긴다** — 이게 경쟁 논리의 엔진이다. 보호자가 사진 많은 시터를 고를 수 있어야
"잘 보이려고 많이 찍는" 압력이 실제로 작동한다.

문구도 벌점 → 권유로: *"사진이 없어도 제출할 수 있어요 — 다만 사진이 보호자가 가장 안심하는 방법입니다"*

## C. 느슨한 시간대 (사용자 제안)

> "꼭 정확한 시간이 아니라 1~2시쯤처럼 선택도 필요할 것 같아"

- 일정 행에 **`~쯤` 토글** — 누르면 종료 시각 입력이 추가되어 `13:00~14:00쯤` 범위가 됨. 다시 누르면 `정각`
- 시터·보호자 타임라인에 `~14:00쯤` 표시
- 지연 무벌점 원칙과 한 몸 — 정확한 시각 강제는 애초에 우리 설계와 안 맞았다

## 검증 (브라우저)
- `~쯤` 토글 → timeEnd 저장, 입력 2개, 버튼 `정각`으로 전환 ✅ / 타임라인 `~11:00쯤` ✅
- 점수 표기 전 화면 제거 (0.5점 grep 0건) ✅ / 설명 제출도 1건 집계 → `약속 이행 97% (501/515건)` ✅
- 비율 공개 유지: `사진 인증 476건 / 설명 인증 25건` ✅

## 이 수정이 틀렸다면
- **설명만 쓰는 시터가 실제로 늘어난다** → 경쟁 압력 가설 기각. 가중치 복원 검토 (사용자 가설이 걸린 지점)
- **비율 공개가 낙인이 된다** → 사진 못 찍는 정당한 사정(야간·비)이 벌점처럼 작동
- **범위 시간이 알림과 충돌** → "1~2시쯤" 알림은 언제 울리나? 시작 시각 기준으로 정했지만 미검증

# 19차 수정 — 특이사항: 인계 카드의 부활 (2026-08-11)

## 배경 — 실제 보호자 인계문이 들어왔다

사용자가 당근 알바에서 받은 실제 인계문(`08` 자료 #1)을 공유했다. 감자·만두 두 마리의
주의사항 십수 개 — 전부 **특정 행동의 순간에 필요한 정보**였다.

> "기저귀를 갈 때는 입질 방지를 위해 꼭 리드줄을 채운 상태에서" → **배변 인증하는 그 순간에 보여야 한다**

**이것은 피벗 때 버렸던 「시점 순 인계 카드」의 부활이다.** 근본 원인 V2(정보를 수행 시점에
못 꺼냄)에 대한 답이 원래 이거였는데, 매칭 플랫폼 전환 때 통째로 버렸었다.
실제 보호자 자료가 그것이 필요했음을 증명했다.

## 구현 (사용자 제안 그대로)

```
보호자 · 돌봄 일정 화면
  [특이사항] 카드
    공통 | 방석 위에 있을 때는 만지지 말아 주세요...     [삭제]
    밥   | 낯선 사람이 주면 잘 안 먹을 수 있어요...      [삭제]
    배변 | 기저귀 갈 때는 꼭 리드줄을...                [삭제]
    [공통/밥 할 때/산책 할 때/... 선택] + 입력 + [저장]

시터 · 밥 기록 화면
  [참고 사항]
    밥 · 보호자가 남긴 메모 — 낯선 사람이 주면 잘 안 먹을 수...
    공통 · 보호자가 남긴 메모 — 방석 위에 있을 때는...
```

- **한 번 저장하면 계속 산다** — 카톡 장문을 매번 다시 쓰는 문제의 해소
- 항목 종류(`밥/산책/배변/약/놀이`) 또는 `공통`으로 태그 → **그 일을 하는 순간에만 소환**
- 시드 데이터는 실제 인계문에서 각색한 3건

## 검증 (브라우저)
- 일정 화면에 특이사항 3건(밥·배변·공통) 표시, 추가·삭제 동작 ✅
- 산책 특이사항 추가 → 토스트 ✅
- 밥 기록 화면: 밥+공통 2건만 / 산책 기록 화면: 공통+산책 2건만 — **항목별 필터 정확** ✅

## 이 수정이 틀렸다면
- 특이사항이 수십 개로 늘면 기록 화면이 다시 장문이 된다 → 안전(입질 등) 우선 정렬 필요
- 보호자가 구조화(항목 선택)를 귀찮아하고 공통에 다 몰아넣는다 → 시점 소환이 무의미해짐
- **다마리(감자+만두) 지원이 없다** — 실제 인계문은 두 마리였다. 프로토타입 한계

# 21차 수정 — 일기장을 아이당 한 권으로 (2026-08-11)

## 사용자 정의
> "돌봄 일기는 곧 내 경력과도 이어지는데, 내가 만두를 돌봤으면 1개의 글이 생성되고
> 그 안에서 매일매일 있던 일을 확인할 수 있으면 좋을 것 같아"

낱장 일기(시간순 피드)를 **아이당 한 권의 일기장**으로 재구성했다.

```
내 프로필
  돌봄 일기
    만두의 돌봄 일기   3편 · 최근 2026.08.11   [펼쳐보기]
    감자의 돌봄 일기   1편 · 최근 2026.08.06   [펼쳐보기]
    콩이의 돌봄 일기   1편                     [펼쳐보기]
    [새 아이 일기장 만들기]
       ↓ 펼치면
  만두의 돌봄 일기 — 매일의 기록이 시간순으로
       ↓
  공개 프로필: 「돌봄 일기 · 3권」 + 권별 미리보기
```

**왜 이 구조가 나은가:** 일기장 목록 자체가 **돌본 아이 목록 = 경력**이 된다.
낱장 피드는 "부지런히 쓴 사람"을 보여주지만, 권 단위는 **"몇 아이와 관계를 맺어온 사람"**을 보여준다.
경쟁사 검증에서 세운 축("회계는 남는다")의 일기판 — 관계가 권으로 남는다.

- 구버전 낱장 데이터는 「지난 일기」 한 권으로 자동 이전 (localStorage 마이그레이션)
- 새 일기장은 아이 이름 입력으로 시작. 기존 일기장에선 이름 입력 없이 바로 씀

## 검증 (브라우저 전 구간)
- 목록: 만두 2편·감자 1편 시드 표시 ✅ → 펼쳐보기 → 권 내부 시간순 ✅
- 기존 권에 오늘 일기 추가 → 3편 ✅ (이름 입력칸 없음 확인)
- 새 일기장(콩이) 생성 → 즉시 그 권으로 이동 ✅
- 공개: `돌봄 일기 · 3권` + 권별 미리보기 ✅

## 이 수정이 틀렸다면
- 같은 아이를 두 번 돌보면 일기장이 중복 생성될 수 있다 — 이름 매칭 없음 (프로토타입 한계)
- 권이 수십 개가 되면 프로필이 길어진다 → 접기/더보기 필요

# 22차 수정 — 일기장 = 시터 후기 + 공개 기록 링크 (2026-08-11)

## 사용자 정의
> "돌봄 일기는 펫시팅을 마친 후 해당 동물에 대한 펫시터의 후기 +
> 일정 그대로 작성했던걸 다른 사람도 볼 수 있게 공개하는 링크 두가지로 구성되면 좋겠어"

일기장 한 권을 **두 층**으로 재구성했다.

```
만두의 돌봄 일기 (한 권)
  ① 시터 후기 · 내가 씀        ← 주관. 매일의 일기 (기존 entries)
  ② 돌봄 기록 · 검증됨         ← 객관. 일정 그대로 남긴 인증 기록의 공개 링크
     🔗 2026.08.11 돌봄 기록 보기
```

**왜 이 구조가 서비스의 축과 맞는가:** 이 서비스의 정체성은 "감시가 아니라 회계"다.
일기(감성)만 있으면 경쟁사의 자랑 피드와 다를 게 없다. 일기 옆에 **편집 불가능한
검증 기록 링크**가 붙는 순간, 일기의 말("잘 놀았어요")을 기록(제출 시각·사진·보호자
확인)이 뒷받침한다. 기존 정직 표기 체계 그대로: 후기는 「내가 씀」, 기록은 「검증됨」.

- 새 화면 `careRecord`: 그날 일정 전체를 읽기 전용 타임라인으로 렌더
  (제출 시각 · 사진 · 시터 설명 · 보호자 확인+리액션 · 미제출은 「기록 없음」 그대로)
- 진입점 둘: 시터 일기장(②섹션) / 공개 프로필 일기 카드 (`공개된 돌봄 기록 보기`)
- 링크는 `finished` 이후에만 노출. 미완료 시 "돌봄을 마치고 보호자가 동의하면…" 안내
- **보호자 동의 전제**: 화면 상단에 "보호자 동의를 받아 공개된 기록입니다" 명시.
  프로토타입은 동의를 받은 것으로 가정 — 실서비스에선 보호자 측 동의 토글이 필요 [설계 부채]

## 검증 (브라우저 전 구간, ?v=13)
- 전 일정 설명 제출 → 돌봄 마치기 → 일기장 ①/② 라벨 · 기록 링크 노출 ✅
- careRecord: 동의 문구 · 제출 시각 · 시터 설명 · 보호자 확인+고마워요 · 편집 불가 힌트 ✅
- 미완료 상태에선 링크 대신 안내 문구 ✅ (finished 게이트)
- 공개 프로필 → 기록 링크 → careRecord → 뒤로 = verify 복귀 ✅ / 시터 뒤로 = diaryBook ✅

## 검증 도구 사고 기록
- 프리뷰 스냅샷 모드에서 `location.reload()`가 무시되고, navigate 리로드는 localStorage를
  초기화한다. 상태 주입 검증이 두 번 헛돌았다 → **한 페이지 수명 안에서 실제 UI 플로우로

# 27차 수정 — 사용 피드백 일괄: 입력 UI 다듬기 (2026-08-12)

# 32차 설계 — V1 배포 전략에 따른 온보딩 여정 (2026-08-12, 설계만)

## 사용자 정의
> "V1에서는 내가 펫시터고, 당근으로 알바를 구하면 그 보호자에게 이 앱을 보내서 쓰게
> 한다. 보호자가 링크를 받았을 때 온보딩 > 보호자 프로필 > 아이 프로필 > 돌봄 일정
> 작성으로 이어져야 한다."

**V1 재정의: 마켓플레이스가 아니라 시터 개인의 도구.** 매칭은 당근이 담당.
첫인상 = "알바 시터가 보낸 링크를 여는 보호자". 링크를 보내는 행위 자체가
시터의 신뢰 신호(기록을 자처하는 시터)다.

여정: 시터 초대 링크 생성 → 보호자 초대 랜딩(시터 이름 먼저·가치 한 줄·콜드스타트는
약속 프레임) → 아이 프로필(이름만 필수, 특이사항 스킵 가능, 아이 추가) → 보호자

### 버그 2 — `.catch()`를 붙인 저장이 아예 실행되지 않았다
Supabase 쿼리 빌더는 `then`만 구현한 thenable이라 **`catch`가 없다.**
`api.saveItem(...).catch(...)`는 TypeError로 죽고, `then`이 호출되지 않아 **요청 자체가
나가지 않았다.** 화면만 바뀌고 DB는 그대로 — 낙관적 갱신이라 눈에 띄지도 않았다.
→ 쓰기 함수를 전부 `async` 래퍼로 감싸 진짜 Promise를 돌려준다.
**교훈: 붙여놓고 잊는 호출은 반드시 DB로 결과를 확인한다.**

### 일정 입력 버벅임
항목을 하나 고칠 때마다 `saveItem` → **계약 전체 재조회 → 전면 재렌더**였다.
→ 낙관적 갱신(로컬 반영 후 저장은 뒤에서). 재렌더 4ms, 저장 결과는 DB로 확인 ✅

### 46차 보강 — 목록 간격의 정체
> "border-line은 어디에 위치하는거야? border-line 사이에 불필요한 간격이 계속 관찰되고있어"

필요하면 「번호 공개」를 시터가 켜는 옵션으로 다시 논의한다.

## 52차 — F16 양방향 알림 종 (2026-08-12)
보호자 종 = 새 인증 / 시터 종 = 보호자 행동. 지금까지 실시간 반영은 있었지만
**종·배지·이력이 없어** 앱을 안 보고 있으면 아무것도 남지 않았다.

### 알림은 트리거가 쓴다 (마이그레이션 16)
클라이언트가 빠뜨릴 수 있으면 알림이 아니다. **행이 바뀌는 그 자리에서** `events`에 적는다.
- 보호자 → 시터: 확인 완료 / 일정 전달 / 픽·드롭 수정 / 약속 장소 주소 / 특이사항 / 리액션
- 시터 → 보호자: 새 인증 · 다시 제출 / 먼저 챙긴 순간
- 특이사항은 계약이 아니라 보호자에 달려 있어, **그 보호자의 진행 중 계약**에 붙인다

종을 여는 것이 곧 열람이다. 보호자 쪽은 화면을 열 때 `seens`를 남기고(따로 누를 필요 없음),
양쪽 다 화면을 **먼저 그린 뒤** 읽음 처리해 NEW가 한 번은 보이게 한다.

### 버그 — one-to-one 관계는 배열이 아니다
`proofs`를 `verdicts(*), seens(*)`로 조인하면 `proof_id`가 PK라 PostgREST가 **객체(또는 null)**
를 준다. 배열로 알고 `.length`를 세면 값이 있어도 `undefined`라 **「확인했는데 NEW가 안
사라지는」 38차 버그가 그대로 재발**한다. → `hydrate`에서 `verdict`·`seen` 단수 필드로 정규화.
**교훈: 조인 결과의 모양은 관계 종류에 따라 다르다. 세기 전에 실제 응답을 본다.**

검증: 보호자가 특이사항 저장 → 시터 종 배지 1 → 열면 NEW → 나오면 사라짐 ✅ /
시터가 설명만으로 제출 → 보호자 종 배지 1 → 「지금 오는 인증」에 표시 → 나오면 사라지고
`seens`가 DB에 남음 ✅

## 53차 — 펫시터 프로필을 프로토타입과 일치시킴
> "펫시터 프로필쪽은 프로토타입의 프로필 그대로 적용해주라"

hero를 `50% (1 / 2건)` + 설명 + **게이지(.pbar)** 구조로, 보조 지표를 `.minor` 행으로,
문구·순서까지 `verify()` 그대로 옮겼다.

**「신원 인증 · 정부 발급 신분증」 행은 뺐다.** 프로토타입은 하드코딩이었지만, 실제로 확인한
적이 없는 것을 공개 프로필에 쓰면 거짓 표기가 된다. 확인 절차가 생기면 넣는다.
후기 별점(★·후기 n)도 데이터가 없다 — 보호자 후기는 M6.

### 53차 보강 — 프로필의 돌봄 일기 미리보기
> "돌봄 일기 · 2권 … 이거 없잖아"

프로필의 **일기 표시 영역**이 빠져 있었다 → `sitter_public(slug)`이 권수·최근 후기 한 줄·
공개 기록 여부까지 실어 주도록 확장(마이그레이션 17)하고, 「ⓘ 시터 본인이 씀」 라벨과 함께
프로토타입 구조(.imp)로 그린다. 보호자 경로도 같은 RPC를 쓰게 해 두 화면이 갈라지지 않게 했다.

**단, 일기를 쓰는 흐름(F12 돌봄 마치기 → F13 후기 작성)은 아직 없다.** 그래서 현재는 데이터가
0권이라 이 카드가 렌더되지 않는다. 표시할 자리는 준비됐고, 채우려면 F12·F13이 필요하다.

## 54차 — F12 돌봄 마치기 · F13 돌봄 일기 (2026-08-12)

- 시터 「오늘의 돌봄」에 **전 항목을 기록해야** 「돌봄 마치기」가 뜬다. 마치면 후기 화면으로
- **후기는 계약이 끝날 때 아이마다 한 편** (매일 쓰지 않는다 — 사용자가 정한 규칙)
- 「ⓘ 시터 본인이 씀」을 후기 화면·일기장·프로필에 모두 붙인다 (§2-3)
- 「내 프로필 → 돌봄 일기 보기」로 일기장(아이당 한 권)

### 서버 불변조건은 이미 있었고, 실제로 우회해 봤다
| 조건 | 시도 | 결과 |
|---|---|---|
| 전 항목 기록 후에만 `finished_at` | 항목이 남은 계약을 SQL로 직접 마침 | `guard_finish`가 예외 — 마쳐지지 않음 ✅ |
| (책, 계약)당 후기 1편 | 같은 조합으로 한 편 더 INSERT | `unique_violation` ✅ |
| 아이당 일기장 1권 | `unique (sitter_id, pet_id)` | 스키마에 이미 존재 |

검증: 마치기 → 후기 저장 → 프로필에 「돌봄 일기 · 1권 / 후기 1편」과 인용문 표시 ✅

### 버그 — 입력해도 버튼이 안 켜졌다
`disabled`는 **렌더 시점**에 정해지는데 textarea가 다시 그리지 않아, 다 써도 버튼이 잠긴 채였다.
겉으로는 「저장이 안 되는」 것처럼 보인다. → 입력마다 `rerender()`(paint가 커서를 지킨다).
**교훈: 값에 따라 잠기는 컨트롤은 그 값을 바꾸는 입력이 반드시 다시 그려야 한다.**

### 참고 사항 카드 정리
> "· 공통 텍스트 제거, gap 0"
제목에서 「· 공통」을 빼고, 카드 gap이 끼지 않게 `.tight`로 묶었다.

## 55차 — 프로필 정리 · 가져온 후기 · 아이별 일지 (2026-08-12)

### 프로필에서 뺀 것 (사용자 지시)
「이 세 숫자만 보셔도 됩니다」 / 「왜 「사고 0건」이 아닌가」 / 「✓ 이 서비스에서 확인됨」 보조 지표
카드 전부 삭제. **「보호자 확인」 hero도 숨김** — 앱으로 받은 돌봄이 아직 없어 0%로만 보인다.

### 「약속 이행」에 앱 밖 실적을 함께 센다
> "약속 이행은 지금 내 프로필에서는 4건/100%으로 해줘. 당근에서 진행한 4개 후기 첨부할게"

`sitters.offsite_done`(기본 0)을 더해 `(제출+offsite) / (전체+offsite)`로 낸다.
프로필 수정에서 시터가 직접 넣고, 값이 있으면 hero 설명이
**「당근 알바에서 마친 N건을 포함합니다」**로 바뀐다.

**우려 한 번 적어둔다(§2-3).** 이 숫자는 원래 「이 서비스가 확인한 것」 자리다. 앱 밖 실적은
확인 대상이 아니므로 출처를 문구로 밝혔지만, 같은 숫자 안에 섞인다는 점은 남는다.
「이 수정이 틀렸다면」 → 보호자가 100%를 이 서비스의 검증 결과로 오해한다.
그때는 앱 실적과 앱 밖 실적을 **두 줄로 분리**하는 쪽이 맞다.

### F20 가져온 후기
`imported_reviews` + `imports` 버킷. **캡처 없이는 담기지 않는다**(버튼 비활성).
공개 프로필에는 「ⓘ 시터 본인이 올림 · 이 서비스가 확인하지 않음」과 함께 캡처를 그대로 싣는다.

### 보호자 일지 — 아이를 골라 들어간다
> "해당반려동물을 클릭해야 돌봄일지로 넘어가는 플로우"

다견이면 아이 목록(도착 n/m · NEW 배지)이 먼저, 누르면 그 아이의 일지. 한 마리면 바로 열린다.

### 오늘의 기록 → 활동 타임라인
참고 디자인대로 **항목 하나가 카드 하나**. 상단에 상태 칩(밥 완료)과 시각, 본문, 사진,
하단 메타(밖에 있던 시간 · 사진 없이 설명만). 아직 안 온 항목은 회색 칩과 「예정」으로 남는다.

### 55차 보강 — 「약속 이행」 분모에서 아직 안 온 항목을 뺀다 (마이그레이션 19)
`offsite_done = 4`를 넣었더니 83%(5/6)가 나왔다. 진행 중인 휘석2 계약에서 **아직 시각이
오지 않은 항목 1건**을 분모에 넣고 있었기 때문이다. 그건 못 지킨 약속이 아니다 —
돌봄이 끝나기 전까지 시터가 손해를 본다.
→ 분모 = **마친 계약의 전 항목 + 진행 중 계약에서 이미 제출된 항목**. 결과 100% (5/5).

**[추측] 이 지표의 한계**: `guard_finish`가 전 항목 기록을 요구하므로 마친 계약은 언제나
100%다. 즉 「약속 이행」은 사실상 항상 100%로 수렴한다. 변별력은 **보호자 확인·이의·다시
제출** 쪽에 있다. 지금은 보호자 확인 hero를 숨겨둔 상태라, M5 이후 다시 볼 문제로 남긴다.
